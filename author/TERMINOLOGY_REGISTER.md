# Terminology register

Updated: October 21, 2026.

This is an author maintenance aid for the meanings used in the current lessons. It is the seed for the later learner glossary, not an implemented glossary or tooltip system. Existing claim verification dates and applicability limits remain in REFERENCE_RECORDS.md.

A lesson explains each necessary term where it becomes useful. Use the concrete role it plays there: a missing target account, the collected representation, or the operation being attempted. The invariant below controls meaning; it does not require copying a dictionary paragraph into every lesson.

| Term | Meaning to preserve | Boundary to preserve |
|---|---|---|
| Identity | ISC's representation of a person or other entity, connecting relevant attributes, accounts, and access | It is not a target-system account |
| Account | A record used by a person or service in a particular system | The target record and ISC's representation are distinct |
| Source | ISC's configured representation of a system or collection of account data | Creating it does not create or replace the external application |
| Enterprise application | The actual external business software and its own account/access behavior | It is not the ISC access-application configuration or necessarily the same system as the entitlement source |
| Access application | ISC grouping/configuration for source access profiles in requests and configured password-management functions | It is not an SSO trust, native app deployment, new connector, or proof of all application permissions |
| Account source for an access application | Source supplying the relevant account and access data for that configuration | A business-facing name does not prove where the native application account or password lives |
| Access catalog | Discoverable access offerings presented to a requester | It is not a complete inventory of held access or a required additional object named Catalog |
| Requester / recipient | Person initiating a request / identity intended to receive its access | Their eligibility, permissions, and account context must not be treated as interchangeable |
| Access-request segment | Configured audience limiting requester visibility of associated items | Documented on-behalf requests can concern authorized other recipients; it is not universal recipient eligibility or runtime authorization |
| Identity provider / SSO | Sign-in authority / shared sign-in arrangement for participating applications | A catalog or access-application configuration does not establish the application's IdP trust or every permission |
| Application session | Continuing signed-in application context after authentication | It need not immediately reflect a membership change; catalog changes do not prove session termination |
| Connector | The integration used to read data and perform supported configured operations | Read support does not prove write support, privileges, or success |
| Direct connection | Configured connectivity to the external system rather than only an uploaded account export | It does not mean every operation is supported or that all connectors share one hosting path |
| Flat file connection | Account data supplied through a configured file input | For the read-only file source taught here, importing a file is not writing a change into the external application |
| Authoritative source | The source used through an identity profile to establish an identity population | It need not supply every identity attribute and does not imply unrestricted write access |
| Identity profile | Configuration associated with an authoritative population, including identity-attribute mappings and applicable settings | Creating a connection alone does not supply the full population and mapping design |
| Account schema | The source account attributes and their organization, including the designated Account ID and Name | A schema does not confer external read permission or create external fields |
| API / endpoint | A software interface for exchanging information or operations / an address for a particular API service or operation | Access to one endpoint does not prove all read and write operations are available |
| Source owner / entitlement owner | Assigned ownership of the source / of an access item | Ownership can route applicable work; it does not confer external administrative authority |
| Attribute | A named value on a particular record | Identical names on different records do not make one shared value |
| Account attribute | A named piece of information on one source account | Correlation does not turn every account attribute into an identity attribute |
| Identity attribute | Information recorded/calculated on the person-level identity | Its selected input and calculation come from configuration, not merely matching field names |
| Entitlement attribute | Information describing the represented access item | An account field marked Entitlement carries membership/access values; it remains an account field |
| Entitlement type / schema | Kind of access item within a source / its attributes and designated ID/Name | Membership references require the correct source/type relationship and matching designated ID values |
| Mapping | Configuration specifying how an output attribute obtains its input/value | Input selection/calculation does not by itself write back to the source |
| Transform | Configured logic with inputs and outputs for attribute calculations | Calculating an identity value does not rewrite the collected input account value |
| Attribute synchronization | Configured provisioning of selected account attributes from corresponding identity attributes | Eligibility and existing correlation are required; mapped nulls can propagate and target outcomes must be checked |
| Multi-valued | An attribute can hold a collection of values | A list of identifiers is not one joined identifier; support depends on schema/feature |
| Aggregation | Collecting source account or access data into ISC within the applicable scope | It is not itself a grant, and observation is not a perpetual live guarantee |
| Account correlation | Associating a collected source account with the appropriate ISC identity | It does not authenticate a sign-in or create a missing target account |
| Entitlement | An access item represented from a source, such as a permission or group membership | The external system determines its operational meaning |
| Access profile | A bundle of related entitlements from one source | Detection/assignment and original delivery history must not be conflated |
| Role | An access grouping whose assignment represents required access for a responsibility or population | Criteria, requested assignment, and fulfilled target access are different evidence |
| Direct entitlement in a role | A source entitlement included in the role without an access-profile intermediary | It still uses supported source/account fulfillment; it is not a bypass or the same as a direct-permissions schema type |
| Access assignment | Association of access with its recipient under applicable configuration or a request | Definition, assignment, delivery, and current target state are separate |
| Access-profile detection | Recognition during processing that held access matches the profile's entitlement contents | It does not prove ISC originally granted the permissions or a broader role was assigned |
| Requestable | Available to request under the configured process | It does not establish approval or successful delivery |
| Access-object owner | Person assigned responsibility for an access-model object | Ownership does not automatically confer that object's access |
| Revocation versus definition deletion | Removing an applicable access assignment versus removing its model object | Role disablement/deletion and access-profile deletion do not deprovision previously granted access |
| Access request | Asking for specified access for a specified recipient | Request, approval, and delivered access are separate |
| Provisioning | Carrying out supported account or access changes | Initiation or processing completion does not validate target success |
| Deprovisioning | Removing previously granted account access or permissions through the applicable operation | A permission removal need not delete the account or end every session |
| Target system | The system receiving the attempted account or access change | The same external system can supply source data in the read direction |
| Identity processing | Evaluating identity information and applicable configured access | It can initiate changes; it does not prove their target outcome |
| Lifecycle state | A configured business stage used to drive applicable account and access actions | LCS is informal shorthand, not an additional object or guaranteed UI label |
| Certification campaign | The organizing set of access-review work | It is not the individual review assigned to a reviewer |
| Certification | An assigned review within a campaign | Supported decisions depend on the access and assignment model |
| Remediation | Work to carry out an access correction and verify its result | A recorded revoke decision alone is not completed removal |
| Authentication | Verification of a claimed identity under the applicable requirements | Successful authentication does not justify every permission |
| Authorization | Deciding whether an actor may perform a particular operation on a resource | Business approval and runtime application enforcement are distinct contexts |
| Front end / back end | User interface / trusted application processing | Hiding an interface control does not enforce the protected operation |
| Object ID | Technical identifier of a particular ISC record | Establish object type and tenant context; it is not automatically an employee number or source-system key |
| Native identity | Identifier of an account in its source-system context | Connector-specific meaning; do not assume a username, ISC account object ID, or schema-determined UUID is a universal alias |
| Business identifier | Organization-managed identifier such as an employee number | Its uniqueness, stability, and reuse depend on business policy; correlation use does not make it the ISC identity ID |
| Display name | Human-readable label for a represented record | A matching label does not prove identical objects, sources, access, or unchanged native identifiers |
| Reference | Relationship pointing to a particular other record | Resolve the target and its context; reference existence is not proof of business correctness, grant, or target success |
| Account ID / Account Name schema designations | Selected attributes identifying/naming accounts in a source schema | Changing designations after aggregation is different from editing a friendly label and carries documented duplicate/reference risks |
| Entitlement object ID / source value | ISC entitlement-record identifier / access-item value in the source context | Membership linking uses configured type/schema and designated source ID values, not an arbitrary display label |
| Search accountId | Search account-context field using source aiqAccountName when available, otherwise account display name | Do not equate it with account API object id or generalize one interface's field semantics to another |
| Tenant / environment | Particular hosted ISC context / operating context such as production or test | Copied labels and native keys do not prove cross-context object equivalence |
| One-to-many identity/account relationship | One identity can be associated with multiple account records, including multiple accounts on one source | Association does not merge accounts or duplicate person identities; shared-account responsibility is a different relationship |
| Account Attribute transform input selection | Configured lookup of an account attribute; default oldest-first with non-null fallback, subject to filter/sort/first-account settings | This value-lookup default is not a universal provisioning account-selection rule |
| Multiple Account Options | Access-profile account criteria for automatic profile provisioning through role/lifecycle assignment | Not applied to Request Center request selection or a single-account identity on that source; zero/multiple matches fail the applicable provisioning, with manual selection only if enabled |
| Request account selection | Requester chooses the intended source account when the recipient has multiple accounts in the documented Request Center path | Recipient identity, selected account, approval, and delivery remain distinct; an existing profile cannot simply be re-requested for another account |
| Uncorrelated versus incorrectly correlated | Not matched to an authoritative identity versus matched to the wrong identity | Neither is equivalent to an external account disable/delete; uncorrelated-account searches do not expose every wrong-person association |
| Account removal versus external deletion | Removing ISC's representation versus deleting the external system's account | The source account can be re-collected if it still exists; continuing access assignments must also be examined |
| ISC tenant | Particular organizational environment within the hosted service, containing configuration and represented information | Not an external application, identity profile, source, VA cluster, or customer-owned physical server |
| Software as a service / SaaS | Vendor-operated hosted application service | Hosting does not decide business access, correct customer data, supply external credentials/privileges, or verify every target result |
| Operational responsibility boundary | Distinction among service operation, customer configuration/governance, integration dependencies, and target-system enforcement | An investigation map, not a universal blame assignment or contractual SLA |
| Integration identity / recipient account / ISC administrator | Actor connecting to the external system / account receiving the access / actor administering ISC | Different credentials and permissions; tenant Org Admin is not automatic external application authority |
| Virtual Appliance / VA cluster | Customer-deployed Linux-based VM supporting integration / grouping of appliances associated with source work | Not a full tenant or a requirement for every connector; distinguish source association, member connectivity, vendor software updates, and any additional customer-provided OS duties |
| SaaS connector | Supported connector work in SailPoint's hosted runtime, without a customer-deployed VA cluster for that connection | Application hosting location does not select connector mode; external API credentials, privileges, target behavior, operation support and connectivity still matter |
| Sandbox versus production destination | ISC testing environment versus live environment and the actual external system each integration reaches | A sandbox tenant/badge does not itself block writes to a production target or make production data appropriate for all testers |
| Polling / cluster work queue | Running VAs ask for work addressed to their associated cluster / pending connector requests | Documented model, not a claim about exact queue acknowledgements, retry timing, exactly-once effects, or an invariant worker choice |
| Outbound initiation versus work direction | VA initiates required cloud communication while ISC operations originate requested work | Responses return over initiated communication; do not invent an unsolicited inbound connection per operation or confuse cloud reachability with target reachability |
| Pairing / cluster passphrase | Supported appliance registration/configuration with tenant and cluster / consistent cluster setup secret | A saved unpaired record is not operational; setup secret differs from OS login, source credential, and recipient password |
| Cloud Connector Gateway / CCG | Default applicable ISC cluster component for the core VA connector path | Not the entire hosted platform or proof that unrelated standalone component deployments support the intended source work |
| Connected / Busy scope | Documented VA operating state / process unavailable for new processing or updates while busy | Appliance/process health is not a guarantee of every target operation, tenant outage, or successful recovery of prior work |
| High availability / disaster recovery | Capacity/redundancy for component unavailability / recovery after wider failures | Shared hosting/network/target dependencies remain; a separate running cluster is not automatic failover under the documented switch-clusters strategy |
| DNS / TLS / proxy | Name resolution / protected communication with applicable peer-trust checks / traffic forwarding intermediary | Diagnose from the actual VA position; reachability, secure trust, authentication, and operation privilege are separate boundaries |
| Interrupted operation outcome | Recorded response may not establish whether a target change occurred | Inspect actual target and audit evidence before retry; restored VA health does not prove all affected jobs completed |
| Connector runtime | Environment where connector software executes | Distinguish SailPoint-hosted SaaS work from customer VA-based work, browser actions, source labels, and external application hosting |
| API endpoint and external resource scope | Called interface address plus relevant organization/workspace/region context | A reachable endpoint and valid credential can still select the wrong environment; an account string alone isn't destination proof |
| API token / OAuth access token / refresh token | External software credential / limited-access credential under an authorization framework / credential for obtaining another access token where supported | Tokens for ISC and for an external application authorize different services; renewal, scopes, roles and supported authentication methods are connector-specific |
| Client ID / client secret | Registered application's identifier / secret credential used in applicable authentication flows | Client ID alone isn't a password; neither is automatically the recipient's credential or an ISC administrator's authority |
| Credential rotation | Replacing a credential and coordinating the integration's supported update | Creating a replacement externally doesn't update a source still using a revoked token; authentication recovery isn't completed failed work |
| Pagination / rate limit / throttling | Splitting returned records into pages / limits on API use / restricting or refusing work under those limits | A first page or interrupted call doesn't establish collection completeness or account deletion; no universal retries or scheduling are promised |
| VA-to-SaaS source migration | Documented eligible-source transition prepared through a draft and permanent apply process | Not universal conversion, undoable testing, proof of equivalent features/schema/timing, or authorization to retire a shared cluster |
| IQService / Integration Service | Windows service performing supported Windows-side connector work for applicable operations | Not ISC hosted on Windows, a VA replacement, target directory, or universal write-only component; dependency follows connector/operation/fields |
| IQService client user / source service account / Windows service logon | Request admission identity / configured target-operation context / Windows process execution context | Registration and Windows authentication don't grant target authority; scripts and local certificate/file access can involve the process account; role sharing doesn't erase boundaries |
| IQService client registration | Configuring which Windows user identities IQService accepts for request authentication | Doesn't create a Windows account, guarantee its usable credential state, or authorize a target change |
| IQService TLS and client authentication | Protected VA-to-service channel with server-trust checks, plus registered Windows-user authentication for incoming requests | Distinct from IQService-to-target channel and target privileges; no disabling security as a troubleshooting shortcut |
| Certificate / private key / CA trust chain | Identity-to-public-key binding / secret server key / trust path to an accepted issuing authority | Validity, endpoint name, trusted chain and process access matter independently; copied certificate alone isn't a working service configuration |
| IQService handler / ScriptExecutor | Operation-category capability / native before-and-after provisioning script capability | Running service isn't enabled capability; current ScriptExecutor default is disabled and requires TLS plus explicit enablement when needed |
| Native after-script result | Result of supported IQService customization following request processing | After execution isn't proof of primary provisioning success, universal rollback, or a cloud-rule execution guarantee |
| UpdateService | Companion service for supported IQService software updates | Automatic-update capability requires configured supported arrangement; host maintenance, credentials, trust, validation and shared-service impact remain |
| Shared IQService dependency | More than one source or VA path relies on the same Windows-side endpoint | VA cluster redundancy doesn't create an alternative IQService instance or guarantee every operation survives maintenance |
| Connection-test scope | Checks implemented by the selected connector under the tested configuration and time | Successful test isn't every read/write, correct external destination, current future connectivity or verified business access |
| Runtime-relative reachability | Required service can be contacted from the actual execution environment over its configured path | A laptop or different VA member isn't an interchangeable test; cloud communication and target communication are separate |
| Gateway / error origin | Intermediary controlling or forwarding requests / component that produced a reported failure | Response number alone doesn't identify the target, account, missing role, or whether work was forwarded |
| Operation dependency map | Relevant destination, supported configuration, protected path, accepted caller, resource authority, valid input and target conditions must fit | Not a fixed packet order or private execution sequence; pre-call validation and target-side refusal are different possible boundaries |
| Payload / mapping | Information carried in an operation request / connection between represented input and required destination field | Valid credentials don't supply a missing workspace/account value or make a label the target key |
| HTTP response scope | Status plus origin, context and detail classify a response | 400/401/403 aren't unique root-cause diagnoses; 407 concerns proxy admission; 429 concerns rate limiting, not an immediate-repeat guarantee |
| Idempotent operation | Repeating equivalent requests has the same intended target effect as one request | Not universal connector behavior, identical responses, no logging/side effects, or permission to blindly retry unknown outcomes |
| Repair / reconciliation / target verification | Restore prerequisite / establish and recover actual work outcome / check intended target state | One doesn't establish the other; timeout and older collected state don't prove no change |
| UI / frontend / backend | Human-facing controls / presentation and interaction / hosted processing of relevant operations | Roles in a conceptual explanation, not evidence of private architecture or identical public endpoints behind every button |
| Platform capability / API contract | Supported operation / documented input, permissions, response and behavior for an API | Starting route doesn't define the operation's effect; public doesn't mean unauthenticated, and undocumented browser calls aren't a supported integration contract |
| API client / SDK / CLI | Software making calls / supporting call libraries / text-command interface | Tooling doesn't create authority, supply missing inputs, add capabilities or bypass downstream connectors |
| ISC user level and token scopes | Applicable platform permission boundary plus token-specific API permissions | Scope doesn't grant authority outside user context; user-associated and client-only credentials aren't interchangeable for every endpoint |
| ISC PAT and access token | User-associated client credential mechanism / token presented to the resource API under its supported rules | Client ID identifies the credential, client secret obtains a token in the applicable flow; none is the target connector's credential or proof of every API permission |
| Request reference versus object/account reference | Identifier for tracked request / identity or access object / external recipient account | Preserve their distinct roles; accepted asynchronous work isn't approval or target completion, and stopping the caller isn't cancellation |
| Automation / ISC Workflow | Configured software-driven work / supported trigger-and-step definition managed within ISC | External schedulers and Workflows are different mechanisms; not every internal ISC process is a custom Workflow |
| Workflow trigger/filter/action/operator/execution | Start/input condition / event narrowing / selected work / path/data control / one run | Filtered-out event isn't a failed run; successful path or notification doesn't prove an access grant; saved definition isn't a real execution |
| Status query versus new command | Inspect a tracked object's state / submit additional work | Refreshing views or seeing older collected state isn't authority to duplicate writes |
| API public/experimental/version boundary | Supported contract and stability conditions for a selected service | Don't freeze old version names, infer parity from browser calls or use an experimental contract as a universal production promise |
| Authoritative source versus authentication source | Accounts establishing ISC identities versus configured source checking credentials for Directory Connection | HR can supply identity data while a separate supported source authenticates the user; neither role implies universal password sharing |
| Native / directory / federated ISC sign-in | Site credentials / supported source credential check / trusted IdP authentication result | Alternative configured routes, not a mandatory chain; normal configured SSO takes precedence over Directory Connection |
| Federation / service provider / SAML assertion | Accepted cross-service authentication trust / receiving service / structured authentication statement | In the taught relationship ISC is the SP; no user password is copied through an assertion and no trust for every business app is implied |
| SAML entity ID, signing trust and identity mapping | Participant identifier, trusted signing identity, and selected ISC attribute matching the authenticated user | Valid IdP authentication/signature does not by itself establish the correct ISC identity match; matching is not source account correlation |
| JIT account creation into ISC | Separately configured sign-in-time account/identity creation arrangement | Not default SSO behavior, every external account's provisioning, or JIT access activation |
| PTA / Directory Connection | Supported source-account credential check used for configured ISC sign-in | Depends on configured account/source/integration; account selection isn't inferred from a provisioning choice, and unreachable is not wrong-password proof |
| MFA / TOTP / recovery verification | Multiple factor categories / time-based code from registered authenticator material / proof for the selected recovery flow | IdP and ISC challenges have separate owners; changing a password doesn't reset an authenticator; password-policy enforcement and identity-profile recovery methods differ |
| Password Management / Password Manager | Supported configured source-password operations / user-facing application/group view | Does not reveal existing passwords or make flat-file sources password-manageable; a correlated account is not sufficient configuration |
| Shared-source password versus sync group | Applications using one account-source password versus supported propagation across different sources | Neither is SSO; a direct external password change isn't proof of reverse propagation; per-source failures and PTA-specific gating matter |
| Password reset / unlock / reenable / MFA reset | Change credential / remove applicable lockout / reverse administrative disablement / reset affected verification registration | Separate operations and authority; recovery verification or a sent email doesn't establish target delivery or justify reenablement |
| ISC and IdP session boundaries / SAML Single Logout | Continuing authenticated contexts and protocol-level coordinated sign-out | ISC does not support SAML SLO; logout redirect, browser closure or password change isn't proof that every external session/token ended |
| Emergency access | Approved controlled alternative sign-in for authorized elevated users during normal-path failure | Not a universal employee bypass or a replacement for configured authentication, MFA, testing and credential ownership |
| Accepted work / asynchronous processing / queue | Initiating operation accepted before later processing completes / deferred completion / work awaiting processing | 202 access-request submission isn't approval or delivery; no private queue layout, scheduling order or completion time is implied |
| Approval / execution / target result | Recorded configured decision / attempted supported work / effect at intended external account | Business approval doesn't supply connector privilege; a failed overall action can retain successful component effects |
| Account activity status and stage | Tracked action's condition/outcome and progress | Distinguish request item, activity, component, collection and actual target scope; requester/recipient labels don't identify every technical credential |
| Partial outcome / rollback | Some intended effects applied / defined undo behavior | Overall failure isn't no effect; no universal transaction or automatic reversal across connectors, entitlements or request items |
| Evidence reference and timestamp | Recorded object relationship plus the event/time it describes | Similar IDs/names don't establish linkage; last-modified isn't necessarily target-effect time; compare tenant, source, account, action and time zone |
| Collection versus delivery evidence | Represented source data under a known read scope/time versus account-changing work/result | Successful aggregation isn't a permission grant; old views don't disprove later target changes; single-account aggregation isn't identity-attribute sync |
| Audit event / task / job / indexing | Recorded occurrence / tracked work unit / preparation of information for search | Different record scopes and update behavior; a missing filtered/page/retained result isn't proof that nothing occurred |
| Reconciliation and current authorization | Establish actual completed/pending/unresolved effects and present authority before supported recovery | Restored prerequisite isn't retried work; prior approval doesn't justify replaying withdrawn access; duplicate protection and idempotency are operation-specific |
| Manual and ticket fulfillment | Person performs required external change / supported service-management integration coordinates work | Marked-complete task or mapped closed ticket is a completion assertion, not independent target measurement; not extra stages for every automatic source |
| Source purpose / represented population / coverage boundary | Agreed external context, account set, information and operation responsibility / intended account set / explicit inclusions and exclusions | Population here is a design concept, not a mandatory new ISC object; a product name doesn't establish environment, people/account count or complete coverage |
| Intended / readable / selected / collected account sets | Project agreement / available under destination and authority / chosen by supported read or export / returned and processed in a particular run | Working connection and successful selected-set run aren't full project coverage; counts can match while membership differs |
| Human standard/admin versus service accounts | Distinct account purposes within the supplied classification | Multiple accounts can belong to one person; disabled accounts still exist; exclusion from one source isn't approval or governance exemption |
| Collection filter versus view filter | Selection affecting acquired records versus narrowing already represented results | Missing account and hidden result are different; neither filter is an undocumented write-security boundary |
| Uncorrelated versus uncollected account | Represented account lacks the intended person association versus expected account wasn't acquired | Matching rules can't correlate a record never read; broadening a read doesn't supply missing ownership values |
| Account key versus person-matching reference | Identifier distinct within the external source context versus shared person reference such as employee number | Two legitimate accounts can share a person key; do not substitute it for a unique account identifier |
| Source owner versus external privileges | Assigned source responsibility versus effective authority in the managed system | Naming an owner doesn't grant target privileges, classify all accounts or make the owner responsible for every account by default |
| Coverage evidence and scope change | Comparable expected/collected membership plus data/context validation; approved revision of that boundary | Neither omissions nor a changed read selection establish target deprovisioning; deletion/reset/recreation have separate consequences and are not first diagnostic steps |
| Authoritative / non-authoritative source | Profile-backed identity origin versus additional source-account responsibility | Not a trust score, HR-product restriction, authentication role or connector write-capability upgrade; uncorrelated-account shadow placeholders aren't successful personnel onboarding |
| Applicable identity profile / profile priority | One profile per identity; highest precedence among profiles whose authoritative accounts belong to that identity | Lower numerical value has higher precedence; creation-order default isn't business intent; priority doesn't merge separate identities or imply last-aggregation wins |
| Attribute sourcing / explicit fallback | Supported mapping inputs and calculation conditions / a designed alternative input | Non-authoritative sources can supply identity attributes; don't invent automatic cross-profile field fallback or generalize department/email behavior to manager correlation |
| Required identity attributes / identity exception | Populated uid, email and lastname with unique uid / reported missing or invalid required identity data | Successful collection isn't valid identity establishment; non-null email validation doesn't prove format, delivery or operational suitability |
| Authoritative-account presence / status / removal | Actual account association versus a field value versus removal under supported deletion conditions | Status changes and outages don't establish profile fallback; account removal and profile deletion have conditional identity/dependency consequences, not universal immediate external deprovisioning |
| Capability matrix / operation-object scope | Documented support by operation and object type, including notes and conditions | A user-account check mark doesn't transfer to contacts/groups or another connector family; missing/blank evidence isn't assumed support |
| Connector support / project readiness | Available integration behavior versus a configured, authorized and verified implementation for a stated scope | Operation names or provisioning feature flags don't invent target APIs, implement endpoints, supply valid input or prove completed effects |
| Read group / add membership / create group | Collect access-object details / assign an existing right to an account / establish a new access object | Account or entitlement aggregation isn't a write; adding/removing membership doesn't create/delete the group itself |
| Unsupported / unconfigured / unauthorized / invalid input / untested | Different reasons a proposed operation lacks readiness or a request fails | Diagnose the actual operation, caller, object and evidence; don't infer missing capability from one rejection or infer readiness from another successful action |
| Disable / enable / delete / unlock / password change | Distinct supported account effects with target-specific conditions | Deprovisioning isn't a universal delete operation; disabling needn't erase memberships or end every session; imported status isn't the external change |
| Operation-readiness review | Human review of target effect, support, API/runtime, configuration/input, authority and outcome evidence | Dependency arrows aren't a private ISC execution sequence; test-connection success isn't an operation-by-operation acceptance test |
| Explicit fulfillment route | Approved automatic, manual or supported ticket-coordinated route to the intended target effect | Failed direct writes don't guarantee automatic task fallback; certification decisions and completed tasks aren't independent target-state measurements |
| Schema definition / collected account value | Field and designated-use configuration versus information on a particular represented account | Defining office doesn't populate it, create an external field or prove new collection; schema-change audit evidence isn't target-change evidence |
| Schema identityAttribute / displayAttribute | Attribute names used for account identification / designated naming-display input | Values select fields, not a particular employee or account; identityAttribute isn't person-correlation configuration or an identity-profile selection |
| Designated Account Name / descriptive fullName | Schema-selected account-naming attribute versus an ordinary descriptive value in the example | Account Name isn't an unrestricted cosmetic label; post-aggregation designation changes have documented duplicate/reference consequences |
| Account key / person reference | Distinguishes represented accounts in intended source context / connects accounts to their owner under configured matching | Two legitimate accounts can share employeeNumber; correlation doesn't supply missing keys or resolve conflicting account identification |
| Schema discovery / downstream refresh | Supported import of external field definitions versus subsequent collection/processing | Discovery isn't universally supported or a business identifier decision; saving a schema isn't every account refreshed; connector-specific replacement/removal behavior matters |
| Composite account key / source boundary | Deliberately agreed combination of identifying components / configured system and environment scope | Neither concatenation nor changing source boundaries is an automatic safe migration for overlapping identifiers on an existing source |
| Type / cardinality / wire format | Kind of value / one value versus a collection / transport representation | STRING can be multi-valued; a DATE type doesn't choose an arbitrary string's input format; schema metadata isn't universal parsing or coercion |
| Conversion / coercion / normalization | Agreed representation change / implicit conversion / agreed consistency cleanup | Not default permission to strip zeros, lowercase every identifier, join memberships or interpret any non-empty text as true |
| JSON Boolean/string/array/null | Structured values with distinct types and shapes | false differs from text false; one joined item differs from two items; JSON has no native date type; zero and false aren't absence |
| CSV columns / inner list delimiter | Outer record parsing versus field-specific list interpretation | Quoted commas can belong to one field; semicolon/pipe conventions aren't universal ISC defaults or global separator rules |
| Omitted / null / empty string / whitespace / empty list | Distinct original data states | Need read completeness and operation-specific semantics; none alone proves target clearing or access removal; an invalid parse isn't a trustworthy empty-state assertion |
| Date / timestamp / offset / epoch units | Calendar representation / date-time instant / UTC displacement / count from a defined epoch | Day/month meaning and seconds/milliseconds require explicit contracts; date-only expiry doesn't select an hour/zone or prove deprovisioning |
| Multi-value versus entitlement flags | Collection shape versus access interpretation | Phone-number collections aren't automatically entitlements; account-schema Boolean attributes cannot be marked as entitlements |
| Character encoding / evidence chain | Byte-to-character agreement / raw input through extraction, conversion, schema and consumers | A blank UI cell doesn't identify original null/missing state; downstream text typing can't restore already-lost zeros or corrupted characters |
| Membership reference / entitlement object | Account value naming access held / record describing that access | A catalog object doesn't prove a particular account holds it; a collected membership doesn't guarantee rich object details |
| Entitlement type / native object type | Supported access category / category exposed by the external integration | Connect the account attribute and entitlement schema under connector requirements; don't invent types, merge same-looking IDs or reuse one type for multiple account attributes |
| Entitlement ID / Entitlement Name | Selected source-object identification / display attributes and their values | groupKey versus G-206 and label versus Expense Approvers; technical or friendly names aren't automatically keys; ISC record/schema IDs are separate; post-aggregation redesignation can duplicate entitlements |
| Membership linking / account correlation | Connects access references to access objects / connects accounts to their owning identities | Employee-number matching doesn't repair a wrong group identifier; source/type/value context matters |
